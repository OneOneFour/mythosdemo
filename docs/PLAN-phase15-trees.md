**Status: PROPOSAL. Nothing here is committed.** Part of wave 4; see
`docs/PLAN-phase13.md` §1 for the wave map.

**This phase shares a budget with, and now also a design dependency on,
`docs/PLAN-phase14-mining-and-drops.md`, and must land after 14a.** Both add

## 1. The brief

> When a tree is fully felled, it should drop a **seed**, which can be
> planted, and the seed slowly grows into a new tree over real time
> (deterministic — `clock.t`-driven, never `rand()` in a render path).

Three mechanics: a drop condition nothing can currently express, a plant
verb that *almost* exists, and a timed model transition that has no home.

## 2. Recon

### 2.1 A tree is N stacked native `timber` tiles and nothing else

No record, no id, no entity anywhere in `model/`. Generated by
`rules/generate.js:282-295`'s `trees` strata handler (the last entry in
`KINDS`): per column, roll `row.chance`, skip the spawn shelf, scan down from
`fromTy` for the first solid tile, then stack `randInt(height[0], height[1])`
**NATIVE** `timber` tiles upward from it.

Content row, `data/world.js:110`:

```js
{ kind:'trees', sub:'timber', fromTy:10, toTy:28, chance:0.06, height:[3, 5] }
```

**The canopy is purely geometric and carries zero state.**
`view/paint.js#decorate` draws the crown when the substance's `look.canopy`
is set, `skyExposedAt` is true for the tile above, and
`formOf(tile) === NATIVE` (so a *placed* log never grows a crown — only a
natural trunk). Chunk invalidation already covers the crown's reach:
`view/treatments.js#EXTENT.canopy` is 4 tiles either side and sizes
`paint.js#DECO_MARGIN`, and `model/tiles.js#write.touch` plus
`paint.js#stackVer` already bump and sum the right 3×3 neighbourhood.

**Consequence, and it is the single best piece of news in this document:
felling is already free from the view's perspective.** Mine the top trunk
tile and the one below becomes sky-exposed and grows its own crown on the
next repaint, with no code. So **a grown tree needs no view work at all** —
write native `timber` tiles upward exactly the way worldgen does and the
existing rendering handles the rest.

### 2.2 Felling has no tree-specific logic, and `data/drops.js` cannot express one

`rules/mining.js:175-187` is the same code that breaks granite: read
`dropOf()` → `SUB.timber.tile.drops === 'log'` → clear the tile → spawn a
falling `timber/log`.

The existing "mining X also drops Y" hook is `data/drops.js`
(`trigger:'mine'`, `minTier`, `chance`, `give`), rolled at
`rules/mining.js:197-206`. **It cannot express this drop**: a `DROPS` row
sees only the tile just broken, never the state of the column, and "the last
remaining trunk tile" is a column fact. So this needs a real code change in
`rules/mining.js` — which is the only file that can make that decision.

### 2.3 Planting: `placeTile` is the right path, with one real gap

`rules/placement.js#placeTile` (`:191-213`) is form-gated
(`if (!FORM[form]?.tile) return no('THAT DOES NOT BUILD')`), checks bounds,
checks the target is AIR, checks the pockets, checks **backing**, then spends
one unit and writes the tile. Exactly what planting wants.

The gap is the backing predicate (`:204-206`):

```js
  const backed = solidAt(band, tx - 1, ty) || solidAt(band, tx + 1, ty)
              || solidAt(band, tx, ty - 1)
              || climbAt(band, tx, ty - 1) || climbAt(band, tx, ty + 1);
```

Left, right, **above**, and a climbable above or below. **There is no
`solidAt(band, tx, ty + 1)`** — nothing checks for a floor. A seed dropped on
open flat ground, with soil directly beneath it and air on both sides and
above, is **refused today** with `'IT NEEDS SOMETHING TO HANG FROM'`. Which
is correct for a ladder rung and exactly wrong for a seed.

This is not a bug to fix in place: adding solid-below to the shared predicate
would also let a rung or a `block` be placed standing on a floor, which is a
real behaviour change to two other forms. See D15-C.

### 2.4 The form budget

From `docs/PLAN-phase14-mining-and-drops.md` §2.1, executed against the real
modules. `PACKABLE_MAX` is 8 (`adamant`) and does not move, because this
phase adds no substance:

| state | `FORM.length` | `STRIDE` | `PACKABLE_LIMIT` | guard LHS |
|---|---|---|---|---|
| today | 11 | 12 | 20 | 108 of 255 |
| after 14a (`block`) | 12 | 13 | 18 | 117 |
| **after this phase (`seed`)** | **13** | **14** | **17** | **126** |

Safe. **But note what `PACKABLE_LIMIT` 17 means**: ordinals 9–17 are all
occupied by non-packable rows, so appendable headroom for a *tile-capable
substance* is still **zero**, and a future terrain substance must be inserted
below ordinal 17. That correction belongs to 14a (SPEC §15); this phase
inherits it and must not re-derive it.

### 2.5 Four existing shapes for "state that changes over time"

| shape | fit |
|---|---|
| `model/mining.js` — sparse `Map`, band-ordinal-prefixed tile key, seconds as float, `clearAll()` on `newRun()` | **good fit.** Identical addressing need, identical lifetime, and `progressAt` is exactly the 0..1 read a growth stage wants |
| `model/machines.js` — an array of `{band, tx, ty, ...}` records | viable; better if a seed ever needs several fields |
| `model/boons.js` — `{id, left}` decremented by `dt`, never wall-clock | the pattern for "count down, then transition", directly reusable |
| `model/fields.js` — a per-tile `Float32Array` plus an active `Set` | **considered and rejected**, see D15-B |

### 2.6 The schedule is a closed list with a locked tail

`shell/schedule.js`'s `STEPS` array is the entire definition of frame order
(`rules` siblings cannot import each other, so there is nowhere else a step
can hide). It ends `... machines, drive, cycles, tutorial, fields`, and the
file states a hard rule: **`fields` is last**, and the
`tutorial before fields` comment exists *only* to keep that literally true —
"nothing may be appended after it without re-arguing that."

Every adjacent pair in that file carries a comment explaining why it is in
that order. A new step must write two.

The clock a `rules` module uses is `run.t` (ticked first in `STEPS`) and the
`dt` it is handed — never `clock.t`, which is `shell`-owned and unimportable
from `rules`, and never `Date.now()` (invariant 10; SPEC §18.5 makes the same
point about the tribute deadline).

### 2.7 Test coverage today

No test asserts tree count, log count or trunk height — `data/world.js:106-109`'s
"12ish logs" is a comment, not an assertion. One bit-exact baseline exists:
`tests/visual.spec.js:3806-3834` (`tree-chunk-seam.png`), which hand-plants a
5-tile trunk exactly on a chunk boundary to prove the canopy bakes into both
neighbouring chunk canvases. **Unaffected by adding growth** — it tests
existing canopy geometry, not planting — but it moves if
`EXTENT.canopy` or `decorate`'s predicate changes, so neither may.

## 3. The design

### D15-A — the seed drops when the last trunk tile in the column goes

**Recommendation: a local O(1) test in `rules/mining.js`'s break branch, on
the substance and form of the tile just cleared.**

```
after tw.clear(), if the broken tile was NATIVE `timber`:
  if neither (tx, ty-1) nor (tx, ty+1) is now a NATIVE timber tile,
  that was the last tile of that trunk -> spawn ONE `timber/seed`
```

Why the two-neighbour test and not a column scan: a trunk is a contiguous
vertical run, and it is felled one tile at a time in either direction, so the
last remaining tile is by definition the one with no timber above or below
it. Two `subAt`/`formAt` reads, no loop, no state, and it is correct whether
the player fells top-down, bottom-up, or from the middle outward.

`formOf(byte) === NATIVE` (`model/tiles.js:33`) is what keeps a *placed*
timber ladder from dropping seeds — the same free predicate `decorate`
already uses to keep a crown off one. **This got simpler partway through
this document's own life:** `docs/PLAN-phase14-mining-and-drops.md`'s D14-H
deletes `log`'s `tile` block, so a placed ladder can no longer be
`timber/log` at all — only `timber/rung` or `timber/stair`, neither of
which is `timber` in `formOf`'s sense used here (the substance test is
`subOf(byte) === S.timber`, not the form). Concretely: a `rung` ladder is
`{sub: S.timber, form: F.rung}`, so `subOf` still reads `timber` — the
`formOf(byte) === NATIVE` half of the test is therefore still load-bearing
and still correct, doing exactly what it always did (excluding any placed
form), just against one fewer placeable form than it excluded before. Keep
the check as written; the reasoning above is the update, not the code.

**One seed per tree, always** — not a `chance`. A regrowth mechanic that
sometimes gives you nothing is a mechanic that sometimes silently ends the
timber economy, and `log` is the only fuel in the game
(`data/world.js:106-109` says so). If scarcity is wanted later the lever is
the *growth time*, not the drop odds.

**`rand()` discipline.** The seed spawn is a new `iw.spawn` in the break
branch and therefore adds `rand()` calls (the toss velocity). Per
`docs/PLAN-phase14-mining-and-drops.md` §2.5, the rare-trinket roll must keep
its position *relative to the material drop* — so the seed spawn goes
**after** the existing `iw.spawn`/`push('drop')` pair and **before** the
`DROPS` loop, and its two `rand()` draws are then a fixed, deterministic
insertion. Say so in the commit; it changes what existing seeds produce
downstream of the first tree felled, which is expected for a new mechanic and
is not a determinism break (`newRun(s)` twice still matches).

### D15-B — growth state is a sparse map in a new `model/growth.js`

**Recommendation: copy `model/mining.js`'s shape exactly.**

```js
/* LAYER model -- accumulated growth seconds per planted seed. */
const key = (b, tx, ty) => b.ord * 0x1000000 + idx(b, tx, ty);
export const grove = { grown: new Map() };
export const write = {
  plant(b, tx, ty)             set to 0
  add(b, tx, ty, secs)         returns the new total
  clear(b, tx, ty)
  clearAll()
};
export const grownAt  = (b, tx, ty) => ...            // seconds
export const stageAt  = (b, tx, ty, total) => ...     // 0..1, for view
export const planted  = () => grove.grown            // for the step to walk
```

A `Map` and not an array of records because there is exactly one fact per
seed and the addressing need is identical to mining's; a `Map` and not a
`Float32Array` because a planted seed is genuinely rare (`fields.js`'s own
sparse argument), unlike `seen`.

`write.clearAll()` goes into `shell/boot.js#newRun`'s teardown beside
`digw.clearAll()` at `:79` — invariant 8, and the reason `docs/FINDINGS.md`
(8d, #2) exists is that a model module with a `clear` that boot forgets is
exactly how a field survives a restart.

**`model/fields.js` was considered and rejected.** It is tempting — a named
scalar field per band with an active `Set` is precisely this data structure
already built, and adding `'growth'` to `data/world.js`'s surface `fields`
array would cost nothing. Rejected on two grounds: `rules/fields.js`'s
`DECAY` table means a field either decays or is explicitly declared not to,
and a growth timer that *accumulates* is the inverse of what that loop does;
and a field is allocated `Float32Array(tw × th)` per band, which is 28 KB for
a mechanic that will have single-digit live instances. The near-miss is worth
recording so the next person does not have to re-derive it.

### D15-C — the plant verb, and the backing gap

**Recommendation: one new optional key on a form's `tile` block, read in the
one place backing is decided.**

```
tile.roots  true -> a solid tile DIRECTLY BELOW satisfies this form's
            backing requirement, in addition to the four existing
            satisfiers. Absent means the existing rule, unchanged.
```

`rules/placement.js:204-206` becomes:

```js
  const t = FORM[form].tile;
  const backed = solidAt(band, tx - 1, ty) || solidAt(band, tx + 1, ty)
              || solidAt(band, tx, ty - 1)
              || climbAt(band, tx, ty - 1) || climbAt(band, tx, ty + 1)
              || (t.roots === true && solidAt(band, tx, ty + 1));
```

One interpreter key, one branch, `rung`/`stair`/`block` behaviour
bit-identical (**`log` drops out of this list under
`docs/PLAN-phase14-mining-and-drops.md`'s D14-H** — it loses its `tile`
block entirely and can no longer reach `placeTile` at all, so it is not a
fourth thing this predicate needs to stay identical for; if 14 has not yet
landed when this phase is implemented, treat `log` as a fourth identical
case in the interim and drop it from the list once 14a merges). That last
property is the whole reason for the flag: adding solid-below to the shared
predicate unconditionally would let a rung be placed standing on a floor
with nothing beside it, which is a real gameplay change to the ladder — and
gating a height gain on state is the exact class of edit `CLAUDE.md` records
wedging a player in their own shaft.

**Should `roots` also require *soil* specifically?** Recommendation: **no**,
not in this phase. "A seed needs earth" is thematically right and would be
`solidAt` narrowed to a `#bulk`-tagged substance — but it is a second
content rule to explain, it makes the verb fail on stone for reasons the
refusal string has to teach, and the interesting decision (where do I spend
90 seconds of growth) is not made more interesting by it. Named here so it is
a deferral, not an oversight. If it is wanted, it is one clause and one new
refusal string.

**No new key binding.** Planting is `cmd.place` on an armed `timber/seed`
pair — the unified LMB placement Phase 12a built, with no special case
anywhere. `rules/placement.js#placeableFromPockets` already lists any
tile-capable form.

### D15-D — the growth step, and where it sits in the schedule

**A new `rules/growth.js`, inserted immediately before `fields`.**

```js
export function step(dt) {
  const total = eff('treeGrowSecs');
  for (const b of bands)
    for (each planted (b, tx, ty)) {
      if (tileAt is no longer the seed) { clear; continue; }   // mined or chasmed
      if (gw.add(b, tx, ty, dt) < total) continue;
      resolve(b, tx, ty);       // clear the seed tile, stack native timber upward
      gw.clear(b, tx, ty);
    }
}
```

`resolve` writes `h` native `timber` tiles upward from the seed's own tile
through `model/tiles.js#write.set(..., NATIVE)` — the same call
`rules/generate.js:293` makes — and then does nothing else. The canopy,
the chunk invalidation and the seam repaint are all free (§2.1).

**Height comes from `hash2(tx, ty)`, not `rand()`.** A positional hash is
deterministic regardless of *when* the seed resolves, which a stream draw is
not: two runs from the same seed in which the player plants at different
times would consume `rand()` at different points and diverge. `hash2` is
already the idiom for positional pseudo-randomness throughout
`view/treatments.js` and `rules/generate.js`'s own jitter, and it consumes
nothing. Range: the same `[3, 5]` `data/world.js` declares for worldgen
trees, read off that row rather than re-literalled — but see the
"explicitly not designed" note about whether a *planted* tree should match a
*wild* one.

**The two adjacency comments the file demands** (§2.6), to be written into
`shell/schedule.js` in its own style:

- `tutorial before growth` — the tutorial step is a pure observer of facts
  another step wrote, and nothing in the beat sheet reads a growing seed.
  This pair carries no freshness argument; growth sits here because the tail
  of the list is where the frame's facts have settled and because `fields`
  must stay last.
- `growth before fields` — `fields last` is a stated invariant of this file
  and this pair is what keeps it literally true, exactly as
  `tutorial before fields` used to. A tile written by `growth` this frame is
  seen by the *next* frame's `light`/`reveal`, which is one frame of latency
  on a 90-second event and therefore not worth reordering the list for.

**Placement in the list rather than earlier is deliberate**: putting growth
before `light` would let a tree that finished growing this frame cast shade
this frame, which is a freshness nobody can perceive on a 90-second timer,
and it would cost re-arguing four adjacent pairs.

### D15-E — the numbers

Two rows in `data/tuning.js`, read only through `eff()`:

| id | kind | base | unit | meaning |
|---|---|---|---|---|
| `treeGrowSecs` | value | **180** | s | a planted seed becomes a tree after this much accumulated simulation time |
| `seedYield` | value | **1** | units | seeds dropped when the last tile of a trunk is felled |

And one form row in `data/forms.js`:

```js
  { id:'seed', label:'SEED',
    size:2, massK:0.1, hudOrder:13,
    tags:[],
    subTags:['organic'],
    tile:{ solid:false, climb:false, hardK:0.05, roots:true } },
```

- `subTags:['organic']` — timber is the only substance that crosses, exactly
  as `log`, `rung` and `brand` already restrict themselves.
- `massK:0.1` — the lightest thing in the game. Mass conservation
  (`tools/content.mjs` assertion 6) is not engaged: no recipe produces a
  seed, so there is no input to conserve against. A tree that yields one
  0.08 T seed and 3–5 logs is not creating mass; the drop is not a
  transformation.
- `solid:false, climb:false` — you walk through a seedling. A seed that
  blocked movement would be a trap you planted for yourself.
- `hardK:0.05` — near-instant to mine back out, so a misplaced seed costs
  nothing to recover. Mining a placed tile returns the pair itself
  (`model/tiles.js#dropOf`), so digging up a seed gives the seed back, with
  no code (and `rules/growth.js`'s own "is the seed still there" check drops
  the growth entry).
- `tags:[]` — deliberately no tag membership, the same reasoning
  `forms.js:145-147` gives for `rung`: a seed is not fuel, ore or anything
  else a selector should be able to find by accident.

**180 s and not 90.** `brandSecs` is 90 and is the game's existing "one long
errand" unit; a tree ought to be more than one errand, and 180 s is about
two cycle-2 deadlines' worth of an eighth (`deadlineSecs` is 480). It is a
guess and is marked as one: it is one tuning row and the acceptance
walkthrough is the measurement.

### D15-F — the growth cue

**Recommendation: a live overlay in `view/scene.js`, sharing the pass
`docs/PLAN-phase14-mining-and-drops.md` D14-G adds.**

A seed tile paints as an ordinary 8×8 timber tile through `paintTile` today,
which is wrong for a 2 px seed and gives no indication of progress. The cue
is three discrete silhouettes derived from `stageAt()` — a seed, a shoot,
a sapling — drawn integer-pixel over the tile, viewport-culled, consuming no
`rand()` and mutating no model.

The overlay and not the chunk bake, for `model/world.js:52-58`'s own stated
reason: a chunk canvas caches the **static rock texture** and a **live
condition** is an overlay pass. Growth is a live condition.

Rejected alternative: **call `model/tiles.js#write.touch` at each discrete
stage change** so the sprite bakes into the chunk. It is legal (`touch` is
exported and a `rules` module may call it) and cheap in the abstract — three
repaints per seed over 180 s, against `REPAINT_BUDGET` 8 per frame. Rejected
because a chunk repaint triggered by something that is not a tile-byte change
is exactly the coupling `world.js`'s comments on `seen` and `light` argue
against, and because the overlay is needed anyway for the sub-stage read.

If Phase 14c has not landed, this phase writes the overlay pass and 14c joins
it; if it has, this phase adds a case to it. **They must not be two passes.**

## 6. Explicitly not designed here

- **Discrete growth-stage TILES.** Two extra forms (`shoot`, `sapling`)
  would let the stages bake into the chunk canvas and need no overlay — and
  would cost two `STRIDE` bytes for every substance and drop
  `PACKABLE_LIMIT` to 15. D15-F's overlay buys the same legibility for one
  form. Recorded because "just add a form per stage" is the obvious first
  idea.
- **A seed requiring soil specifically.** D15-C — one clause and one refusal
  string away, deliberately deferred.
- **Wild regrowth.** Nothing regrows a tree the player did not plant, and
  worldgen's `trees` row is untouched. A world that reforests itself removes
  the reason to carry a seed.
- **A planted tree differing from a wild one.** D15-D reads `[3, 5]` off
  `data/world.js`'s own row. There is a real design question underneath
  (should a *cultivated* tree be taller, or faster, or yield more?) and it is
  a content question for whoever wants it, not a mechanism.
- **Seeds as a crop, a farm plot, fertiliser, or a machine that plants.**
  All of them are a farming subsystem. The brief asks for regrowth.
- **Fixing `data/drops.js` to express column conditions.** §2.2 — the table
  is right as it is; this drop is not a loot roll.
- **The canopy's own appearance.** §2.1 — it already works and touching it
  moves a bit-exact baseline for nothing.
- **A "your tree has grown" journal row.** Rejected for the same reason
  `docs/PLAN-phase14-mining-and-drops.md` §8 rejects "vein exhausted": the
  tile appearing *is* the event, and a notification for something 180 s away
  from any input the player made is noise rather than feedback.

## 7. Risk register

| risk | why it is likely | mitigation |
|---|---|---|
| **A timed transition is the classic framerate-dependent bug**, and this is the first one in the game that is not a countdown someone already tested. | `treeGrowSecs` accumulates `dt`; a `Date.now()` version or a per-frame decrement would both "work" and both drift. `CLAUDE.md` records that a fixed-`DT` harness cannot see framerate bugs. | The step takes `dt` at the fixed 1/120 s substep, and the prompt's step 10 asserts resolution at all 8 framerates the hardness table already sweeps — the one probe shape known to catch this class. |
| **Growth height drawn from `rand()` diverges between two runs of the same seed** depending on when the player planted. | It is the obvious thing to write, and `rules/mining.js` right next door already rolls `rand()` for drops. | `hash2(tx, ty)`, and a probe (step 10) that plants the same tile at two different times in the same seed and asserts identical height. |
| **`model/growth.js`'s `clearAll` is not wired into `shell/boot.js` and a seed survives a restart.** | Exactly what `docs/FINDINGS.md` (8d, #2) records happening to `segments`, whose reset was verified by hand but invisible to the harness. | Step 4 wires it; step 10 asserts the `newRun()` fingerprint with a growing seed live. |
| **`tile.roots` is added to the shared backing predicate unconditionally and quietly changes ladder placement.** | It is one fewer branch, and the four existing satisfiers already read as a list you would just extend. | D15-C gates it on the form's own key, and step 6 requires a test proving rung/stair/block placement is bit-identical (plus `log`, if Phase 14 has not landed yet) — specifically that a rung with only a floor under it still refuses. |
| **The seed tile is solid or climbable and becomes a trap or a free ladder.** | `log` and `rung` are the nearest rows to copy and both are `climb:true`. | `solid:false, climb:false` is stated in D15-E with its reason, and assertion 24 catches the solid half structurally. |
| **`tree-chunk-seam.png` moves** because the growth cue was written into `decorate` or `paintTile` instead of the overlay. | `decorate` is where tree appearance lives today and is the natural place to reach for. | Ownership excludes `view/paint.js` and `view/treatments.js` outright, and the prompt names the baseline that must not move and what it means if it does. |
| **Two overlay passes** — this phase writes one and 14c writes another. | The two phases are parallel-capable and both want "a live per-tile cue". | Step 8 makes it a stated failure condition, and §7 of `docs/PLAN-phase13.md`'s sequencing table keeps only one `view/`-owning phase running at a time. |
| **RESOLVED BY `docs/PLAN-phase14-mining-and-drops.md`'s D14-H, not by this phase — named here so its absence is not mistaken for an oversight.** The original risk: a placed log ladder is `sub:timber`, same as a trunk, and a farmer could place-then-mine logs for free seeds. | `log` had a `tile` block and was placeable before D14-H. | D14-H deletes `log`'s `tile` block, so a placed timber ladder can only be `rung` now, and `formOf === NATIVE` still excludes it exactly as this row originally required. **If this phase is implemented before Phase 14 lands**, treat the original risk as live and keep D15-A's own probe (place a log, mine it, assert no seed) until 14a merges, then delete that probe as dead code testing an unreachable state. |
| **A player fells every tree before ever getting a seed and the timber economy ends** — `log` is the only fuel. | Felling is per-tile and a seed only drops on the last tile of a trunk, so a player who fells three tiles of a 5-tall tree and wanders off gets nothing yet. | Correct and intended: the seed is still there, in the two tiles still standing. But it means "I chopped a lot of trees and got no seeds" is a reachable and confusing state — worth a callout beat if `docs/PLAN-phase13.md` 13d's callout extension lands, and worth naming in the acceptance walkthrough ("fell a tree **completely**"). |
